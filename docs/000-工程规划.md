# 000 · 工程规划 — `aosp-uv-cli`

> 版本：v1.0（000-scaffold）
> 状态：**M0 骨架已完成**。Rust 交叉编译流水线（fetch → cargo --target
> aarch64-linux-android → strip → 门禁 → Release）在 M1 接入。
> 工作区级方案背景见 node-bridge-workspace 的 `docs/aosp+node+python+git运行方案.md`。

---

## 1. 背景与定位

**以 AAR 形式发布的、Android 版 `uv` 命令行可执行**——Rust 交叉编译的 `libuv_cli.so`
（arm64-v8a，exec 型 PIE），rustls TLS 自带根证书。上游无 Android 产物 ⇒ CI 自建
（不下载上游二进制）。与 `python-cli` 组合构成完整 python 工具链。

边界：只管 uv 本体；python 解释器属 aosp-python-cli；venv/环境组合属消费方。

## 2. 版本规则

制品版本 = uv 上游版本，独立 semver；升级 = lock 增项 + CI 重建（uv 发版频繁，
跟随节奏独立于 python-cli）。

## 3. 技术方案

- 制品：`jni/arm64-v8a/libuv_cli.so`（exec 型 PIE，16KB 对齐）；无 assets；
- 构建：`rustup target add aarch64-linux-android` + cargo-ndk；
  `-C link-arg=-Wl,-z,max-page-size=16384`；strip；
- TLS：rustls 自带根证书（Android 无系统证书目录）；
- 门禁：exec profile 同款（ET_DYN/INTERP=系统 linker64/白名单/16K/sha/size），
  `libc++_shared.so` 在白名单内但不随包（由消费方 node-runtime 供给）；
- 命名 `libuv_cli.so`（防与 libuv 库混淆）。

开放问题（M1 拍板）：ring/zstd 等 C 依赖的 NDK 可编性试编；Cargo.lock 依赖 sha 的
记录粒度；`libc++_shared.so` 是否改为随包（若消费方不引 node-runtime）。

## 4. 里程碑

- **M0 骨架（本文件）**：✅
- **M1 首产**：依赖试编 → cargo 交叉编译过门禁 → Release；lock 回写。⬜
- **M2 消费接入**：PTY 回程探针（`uv --version`）。⬜
- **M3 Maven Central**。⬜
- **M4 跟随机制**：uv 新版跟进 runbook。⬜

### 4.1 发布模式（GitHub Release 先行、Maven Central 随后）

沿用 aosp-node-pty 的两段式发布：

1. **先行：GitHub Release（M1，tag `v<uvver>` 推送触发）**——归档
   `uv-cli-v<ver>-android-arm64-v8a.tar.gz`（libuv_cli.so + 元数据 + LICENSES + cargo 依赖
   许可清单）与 `.sha256`，lock 回写；
2. **随后：Maven Central（M3）**——执行口径按工作区
   [`docs/发布到maven-central.md`](../../docs/发布到maven-central.md) runbook（§2 一次性凭据 →
   §4 发布前检查 → §5 上传 → §6 核验回填）；RELEASE=false 默认。

- 与 pty 的差异：版本源 `CLI_VERSION`（= uv 上游版本，独立 semver，无配对；uv 发版频繁，
  跟随节奏独立）；上游无 Android 产物，一律源码自建（runbook §10 已登记本线复用）。

## 5. 质量门禁汇总

exec profile 门禁（同 node-cli）+ 不入库 + 可复现 + 许可（uv 双许可 + cargo 依赖清单随
Release 分发）+ 发布卫生（RELEASE=false 默认）。
